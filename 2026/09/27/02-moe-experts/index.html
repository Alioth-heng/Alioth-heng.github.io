02 MoE：让不同专家分工合作
Published in：2026-09-27 | category： 技术学习 DeepSeek 架构

生活类比：一家医院

想象一家只有”一个全能医生”的诊所：不管你是骨折还是近视，都由他一个人从头学到大。要让他什么都会，他就得极其庞大、极其昂贵。

再想象一家医院：

flowchart TD P[病人来了] --> T[分诊台] T --> E1[心脏科专家] T --> E2[骨科专家] T --> E3[眼科专家] T --> E4[神经科专家] T --> E5[儿科专家] E1 & E2 & E3 & E4 & E5 --> O[诊断结果]

病人先到分诊台，分诊台说”你是骨科问题，去 3 号专家”。于是：医院总共有 5 位医生的工资（总参数），但每个病人只消耗 1 位医生的时间（激活参数）。

这就是 MoE（Mixture of Experts，混合专家模型）的全部直觉。

映射到大模型

医院 LLM（MoE）
病人 Token（一个词元）
分诊台 Router（路由器）
各科室专家 Expert（专家，其实是一个个 FFN 网络）
医院全部医生 Total Parameters（总参数量）
这个病人实际占用的医生 Activated Parameters（激活参数量）

先给几个术语正式登记一下：

  • FFN（Feed-Forward Network，前馈网络）：Transformer 每层中负责”加工”token 的子网络。MoE 就是把这一层复制很多份，每份叫一个”专家”。
  • Router（路由器）：一个小网络，输入一个 token 的表示，输出”该交给哪些专家”的判断。
  • Sparse MoE（稀疏混合专家）：每次只激活一小部分专家的 MoE，与之相对的是所有参数都参与计算的 Dense Model（稠密模型）。

一个极简的数字例子

假设一层有 100 个专家，每个 token 只选 2 个（Top-2 Routing）：

也就是说：计算量变成原来的 1/50，但模型的”知识容量”还是 100 个专家的总和。

回到 DeepSeek-V3

V3 用的是 DeepSeekMoE（V2 论文提出的细粒度专家设计）：

flowchart TD T[Token] --> R[Router 路由器] R -->|Top-8 打分| A1[专家 3] R --> A2[专家 47] R --> A3[专家 201] R -.->|其余 253 个休眠| X[...] T --> S[共享专家
每个 token 都会经过] A1 & A2 & A3 & S --> O[加权组合后输出]

官方技术报告的数字：

  • 总参数 671B，每个 token 激活 37B
  • 每个 MoE 层：1 个共享专家 + 256 个路由专家，每个 token 激活 8 个路由专家
  • 共享专家（Shared Expert）：不管什么 token 都会经过的”全科医生”，负责承载共性知识；路由专家则专注各自的细分领域
  • 61 层 Transformer，除前 3 层外全部换成 MoE 层

所以”671B ≠ 每个都算”的直觉是：671B 是仓库总库存，37B 是每个 token 实际取用的部分。

为什么 MoE 能降低计算量？

回顾第 01 篇的三笔账：MoE 直接砍的是计算量这一笔。

  • Dense 模型：算力成本 ∝ 全部参数
  • MoE 模型：算力成本 ∝ 每个 token 激活的参数（37B），存储成本才是 671B

对训练来说，同样的算力预算下可以训练一个”容量大得多”的模型；对推理来说，每个 token 只需 37B 的计算和访存。

代价是什么？

天下没有免费午餐，MoE 至少带来三样新麻烦（第 03、04 篇展开）：

  1. 显存一点没省：256 个专家全都要装进显存，哪怕大部分暂时闲置
  2. 负载均衡问题：如果所有 token 都挤向少数几个”明星专家”，其他专家白养了，模型还退化
  3. 通信复杂度：专家分布在几百张 GPU 上，token 要跨卡”寄送”到自己被分配的专家那里

⚠️ 常见误区

❌ “MoE 就是多个完整模型拼起来”
不是。MoE 是把 Transformer 内部的 FFN 子层拆成多个专家，Attention 等其他部分仍然共享。它不是 8 个小模型投票，而是每个 token 内部”走一条专家通道”。

❌ “Expert 是像’医学专家’那样有明确分工的”
“专家”是个类比。实际上专家是靠训练自然分化出来的，没有人为指定”这个专家管数学”。DeepSeek-V3 论文观察到细粒度专家确实呈现了一定的功能性分化，但边界是模糊的、学出来的。

❌ “MoE 省显存”
MoE 省计算，不省显存。671B 参数都要放进显存（训练时还要加上梯度和优化器状态），这是 MoE 部署的主要痛点之一。

❌ “激活 37B，所以 V3 等于一个 37B 模型”
能力上 V3 远强于 37B 的 Dense 模型，因为它能从 671B 的容量中按需调用知识。激活参数决定”每步计算量”，总参数决定”知识容量”，两者不能划等号。

自测题：你真的理解了吗？

  1. 一个模型有 100 个 Expert，每个 Token 只激活 2 个。为什么它可以拥有很多参数，却不需要每次计算全部参数？
  2. Total Parameters 和 Activated Parameters 的区别是什么？分别对应”容量”还是”每步计算量”？
  3. 医院类比中，”分诊台”对应 MoE 里的什么？它的输入和输出分别是什么？
  4. DeepSeek-V3 有多少个路由专家、多少个共享专家？每个 token 激活几个路由专家？
  5. MoE 让”计算”变便宜了，那它让”显存”也变便宜了吗？为什么？

参考答案

  1. 因为参数是”存储”，计算是”使用”。每个 token 只需 Router 选出的 2 个专家参与前向计算，其余 98 个专家的参数虽然存在但不参与这次计算——所以容量是 100 个专家的，计算量只有 2 个专家的。
  2. Total Parameters（总参数）是模型包含的全部参数，代表知识容量；Activated Parameters（激活参数）是单个 token 前向传播时实际用到的参数，决定每步计算量。V3 是 671B / 37B。
  3. Router（路由器）。输入是当前 token 的表示向量，输出是对各专家的打分（进而选出 Top-K 个专家及对应的权重）。
  4. 每个 MoE 层 1 个共享专家 + 256 个路由专家，每个 token 激活 8 个路由专家（官方技术报告数字）。
  5. 没有。所有专家的参数都必须常驻显存，无论这个 token 是否用到它。MoE 优化的是计算量（以及随之而来的访存量），显存占用反而比同计算量的 Dense 模型更大。
