06 KV Cache：为什么推理越来越吃显存？
Published in：2026-09-27 | category： 技术学习 DeepSeek 架构

写文章的困境

想象你在续写一篇长文。写到第 1000 个字时，你需要不断回看前面写过的内容：主题是什么、用了哪些论据、埋了什么伏笔。

模型也一样：每生成一个 token，都要参考之前所有 token。 而”参考”在 Attention 里意味着——每个新 token 的 Q 要去和之前所有 token 的 K 做打分、取它们的 V 做加权。

一个糟糕的方案和它的改进

糟糕方案：每生成一个新 token，就把之前所有 token 重新算一遍 K 和 V。

  • 上下文 1000 个 token 时，每生成 1 个新 token 要重算 1000 个 token 的 K/V
  • 上下文 10000 个时，就要重算 10000 个
  • 这是纯粹的重复劳动：前面 token 的 K 和 V 根本不会变（它们的输入没变过）

改进方案：算一次，存起来。这个”存起来的 K 和 V”就是 KV Cache（键值缓存）。

flowchart TD subgraph 生成新 token 时 A[新 token] -->|只算自己的 Q K V| B[新 token 的 Q] B -->|与缓存中所有 K 打分| C[缓存里的 K1..Kn] C -->|按权重取用| D[缓存里的 V1..Vn] end subgraph 显存中 C & D --- E[KV Cache 常驻显存
随对话变长不断增长] end

用空间换时间：计算省了，但显存里多了一块”越聊越大”的缓存。

KV Cache 到底有多大？

给个体感数字（以 V3 这类模型为例，每 token 的 KV 缓存开销 ∝ 层数 × 每层缓存量）：

  • 传统 MHA 下，一个 671B 级别、128 头的模型，每个 token 的 KV Cache 可达上百 KB
  • 上下文 4K token → 缓存约几百 MB/请求
  • 上下文 128K token → 缓存可达数十 GB/请求
  • 同时服务几百个用户 → 缓存占用轻松超过模型参数本身！
flowchart TD A[上下文长度增加] --> B[KV Cache 线性增长] B --> C[显存占用上升
能同时服务的请求数下降] B --> D[每步要读取的缓存数据变多] D --> E[显存带宽压力上升
生成速度下降] C & E --> F[推理成本高、速度慢]

关键认知：推理是”搬运密集型”工作

这里要连接你在第 01 篇学到的 GPU/HBM 知识：

  • 模型参数、KV Cache 都存在 HBM（高带宽显存）里
  • 每生成一个 token，GPU 都要把用到的参数和全部 KV Cache 从 HBM 读一遍
  • GPU 的计算单元很强大，但数据搬运速度（显存带宽）跟不上计算速度——大量时间花在”等数据到货”

所以推理的瓶颈公式大致是：

生成速度 ≈ 显存带宽 ÷ 每步需要搬运的数据量

KV Cache 越大，每步要搬的数据越多 → 生成越慢、同时能服务的用户越少、成本越高。

缓解手段（各有取舍）

方法 思路 代价
减少层数/头数 从源头少存 直接损失模型能力
量化缓存 用更低精度存数字 精度损失
滑动窗口 只存最近 N 个 token 丢掉远距离上下文
MLA（下一篇） 压缩后存 结构更复杂，计算稍多

注意前三种都是”少存东西”或”存得糙一点”，都直接牺牲了什么。MLA 的目标更野心：存得少，但不丢信息。 这就是下一篇的主题。

⚠️ 常见误区

❌ “KV Cache 是模型参数的一部分”
完全不同。参数是训练完就固定不变的”知识”；KV Cache 是运行时随每段对话动态生成的”临时笔记”，对话结束就清空。两者共享显存空间，互相挤压。

❌ “KV Cache 大小是固定的”
它随上下文长度线性增长。128K 上下文的缓存是 4K 的 32 倍——这就是长上下文推理贵的根本原因。

❌ “推理慢是因为 GPU 算力不够”
多数情况下算力过剩，瓶颈是带宽：每步都要从 HBM 搬运海量数据（参数 + KV Cache），搬运跟不上计算。

❌ “没有 KV Cache 模型就不能工作”
没有缓存也能算（每次重算历史 K/V），只是慢得离谱——把 O(1) 的每步工作变成了 O(n) 的重复劳动。KV Cache 是用显存换时间的工程必需品。

自测题：你真的理解了吗？

  1. 为什么每生成一个 token 都需要”参考”之前所有 token？这个”参考”在 Attention 里具体是什么操作？
  2. 如果不使用 KV Cache，每生成一个新 token 需要额外做什么工作？复杂度如何变化？
  3. 为什么说 KV Cache 和模型参数是”两种完全不同的显存占用”？
  4. 如果上下文长度从 4K 增加到 128K，KV Cache 会发生什么变化？进而影响哪两个关键指标？
  5. 为什么说大模型推理是”搬运密集型”工作？这和 HBM 带宽有什么关系？

参考答案

  1. Attention 机制要求每个新 token 的 Q 与之前所有 token 的 K 打分、并加权它们的 V——因为语言的意义依赖上下文（指代、搭配、呼应都要回看历史）。
  2. 需要为之前所有 token 重新计算 K 和 V；每步工作从 O(1)（只算新 token）变成 O(n)（重算全部历史），上下文越长浪费越严重。
  3. 参数是训练后固定的权重（知识本体），所有请求共享同一份；KV Cache 是每个请求运行时动态生成、随对话增长的临时数据，请求结束即释放。二者此消彼长地争夺显存。
  4. 缓存线性增长 32 倍；一是显存占用暴涨、可并发请求数下降（吞吐/成本），二是每步需要读取的缓存数据变多、生成速度下降（延迟）。
  5. 每生成一个 token，都要把参数和全部 KV Cache 从 HBM 读入计算单元；数据搬运总量巨大且受显存带宽限制，GPU 常在”等数据”，所以优化方向是减少搬运量（如 MLA 压缩 KV）。
