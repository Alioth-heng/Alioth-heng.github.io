第二章：使用 NapCat 和 OneBot 给AI接入QQ聊天能力
Published in：2026-10-11 | category： 技术学习 AI 应用

上一章我们让电脑本地跑起了一个大模型，但它只能在你自己的黑框框里陪你聊天。
这一章要做的事是：让它住进 QQ，变成你列表里一个能正常对话的好友。

一、先解决一个根本问题：为什么 AI 不能直接登录 QQ

很多人第一次做 QQ 机器人时会有个朴素想法：既然 AI 能聊天，那给它个 QQ 号密码让它登录不就行了？

不行。而且原因比”技术难”更基础。

原因 1：QQ 没有给 AI 留”官方登录口”

腾讯确实有官方的机器人平台，但那是给企业/开发者申请用的，有审核、有资质要求、能做的事也受限。对于个人玩家，并不存在一个”输入账号密码就能让程序接管 QQ”的官方接口。

原因 2：退一万步，就算有，AI 也不知道怎么”收发消息”

这是更关键的一点。上一章结束时的 Ollama 是什么？是一个在本地 11434 端口上等着接收文字、返回文字的服务。它：

  • 不会登录任何账号
  • 不懂 QQ 的消息格式
  • 不知道”有人 @ 我了”这件事
  • 没法把生成的文字变成一条 QQ 消息发出去

打个比方：你造了一个很会说话的大脑，但它没有手、没有耳朵、也没有嘴。

所以真正要解决的问题不是”让 AI 登录 QQ”，而是：

找一个能登录 QQ 的”身体”，把大脑接上去。

这个”身体”，就是接下来要说的 NapCat。

二、NapCat 是什么：一个能登录 QQ 的”中转站”

NapCat 是一个第三方工具，它做的事可以这么理解：

原理：它启动一个真正的 QQ 客户端（QQNT 内核）并完成登录，然后把这个客户端”收到的消息”和”能发消息的能力”，用程序接口暴露出来给你用。

用人话讲：

  • 它替你登录 QQ（所以你还是需要扫码/账号登录一次，和你平时登 QQ 一样）
  • 登录之后，它一边挂着 QQ，一边把收到的消息转交给你的程序
  • 你的程序算完回复，交给它，它再以这个 QQ 号的身份把消息发出去

所以 NapCat 扮演的是**”QQ 客户端”和”你的程序”之间的翻译官 + 快递员**。

注意：这类工具属于第三方实现，不是腾讯官方支持的接口。用它意味着你要自己承担账号风险（比如异常登录触发风控）。建议用一个专门的、不重要的小号来跑机器人，别拿自己的大号冒险。这一点比任何技术细节都重要。

我实际用的形态

NapCat 在 Windows 上有几种运行方式，我用的是 Shell 模式——简单说就是直接跑它的 node.exe index.js，不去注入或修改 QQ 客户端本体。好处是干净、不容易被 QQ 更新搞坏，出问题重启就行。

三、OneBot 是什么：不同软件之间的”翻译语言”

现在有了 NapCat，它能把 QQ 消息交给程序。但它用什么”格式”交？你的程序又该按什么格式回？

如果没有统一约定，那就会变成：NapCat 用它的格式、你的框架用它的格式，每接一个新工具就要写一遍转换代码。

OneBot 就是为了解决这个而生的——它是一套约定好的消息格式和通信规则（协议）。

原理：协议这个词听着唬人，本质就是”大家事先说好的说话方式“。
就像两个国家的人要交流，可以都改用英语——英语就是他们的”协议”。OneBot 就是 QQ 机器人世界里那门”通用语”。

有了 OneBot：

  • NapCat 说：”我按 OneBot 格式把消息给你”
  • 机器人框架说：”我按 OneBot 格式收，也按 OneBot 格式发”
  • 两边不用认识对方，也能配合

这才是 OneBot 真正的价值：它让”QQ 接入层”和”机器人逻辑层”解耦了。你今天用 NapCat，明天换个别的接入工具，只要它也说 OneBot，你的机器人代码一行都不用改。

四、完整链路：一条消息是怎么走完的

把三章的东西合起来，一条 QQ 消息从发出到收到回复，走的是这条路：

graph TD A["QQ 好友发来消息"] --> B["NapCat<br/>（登录着的 QQ 客户端）"] B --> C["OneBot 协议<br/>转成统一格式"] C --> D["机器人框架<br/>NoneBot2（127.0.0.1:8080）"] D --> E["调用本地模型<br/>Ollama（127.0.0.1:11434）"] E --> F["Qwen3.5-4B<br/>生成回复文字"] F --> G["框架按 OneBot 格式回传"] G --> H["NapCat 发出 QQ 消息"] H --> I["好友收到回复"]

注意 D 和 E 是两个不同的程序、两个不同的端口——这是理解整个架构的关键：

角色 我的实际地址 负责什么
Ollama（大脑） 127.0.0.1:11434 只负责生成文字
机器人框架（神经） 127.0.0.1:8080 决定什么时候叫大脑、怎么回话
NapCat（身体） 反向连到 8080 负责收发 QQ 消息

这三者是独立的进程，靠网络地址互相连接。 记住这一点，后面所有报错你都能自己定位。

五、动手：把链路搭起来

5.1 安装 NapCat

从 NapCat 的发布页下载 Windows 版本，解压到一个固定、不带中文和空格的目录（比如 D:\AI\QQBot\NapCat）。

注意：路径里尽量不要有中文和空格。很多 Node.js 工具在这上面翻车，报错信息还特别难懂。这是省时间的好习惯。

解压后目录里应该有 node.exe、index.js、napcat/ 这些文件。第一次启动它会让你登录 QQ（扫码或账号密码），登录一次之后通常会自动记住。

5.2 配置 OneBot 的”反向 WebSocket”

这是本章最容易被绕晕的地方，我尽量讲清楚。

两个程序要通信，得解决一个问题：谁主动去连谁？

有两种方式：

方式 谁主动 通俗解释
正向 WebSocket 你的程序去连 NapCat 你主动打电话给别人
反向 WebSocket NapCat 来连你的程序 你先把电话开机，等别人打进来

我用的是反向 WebSocket，这也是绝大多数人用的方式。原因很实际：

你的机器人程序（框架）一般会先启动并长期运行，它开一个端口等着；NapCat 启动后主动连过来。这样即使 NapCat 崩了重启，它自己会重新连上来，你的框架不用动。

配置时在 NapCat 里填的是：你的框架在哪个地址等着——也就是 ws://127.0.0.1:8080/onebot/v11/ 这样的地址。

注意：127.0.0.1 就是”本机”。因为 NapCat 和机器人框架都跑在同一台电脑上，所以用本机地址就够了，不需要经过任何网络、也不需要公网 IP。这一点非常重要——整个系统完全在你自己电脑里闭环，消息不需要经过任何外部服务器。

5.3 机器人框架：为什么还要这一层

你可能想问：NapCat 直接把消息给 Ollama 不就行了，为什么要中间插一个框架？

因为”收发消息”之外还有一堆事要处理，这些事 Ollama 一件都不会做：

  • 判断这是私聊还是群聊、要不要回
  • 记住你们前面聊了什么（对话历史）
  • 把历史拼成模型能理解的格式再发给它
  • 模型返回后，决定是发文字、发图片还是发语音
  • 处理并发：几个人同时发消息不能串台
  • 出错时兜底，不能让它崩掉

我用的是 NoneBot2（Python 写的机器人框架），配合 OneBot V11 适配器。它把这些脏活全包了，你只需要写”收到消息后干什么”。

5.5 让它开机自启

和第一章一样的思路，用 Windows 任务计划程序给三个组件各建一个任务：

任务 启动内容
Ollama 启动模型服务
机器人框架 启动 NoneBot2
NapCat 启动 QQ 接入端

我给它们设了开机延迟（错开 30~40 秒），避免几个程序同时抢资源；同时开启”失败自动重启”。这样电脑一开机，机器人就自己上线了。

六、一定会遇到的报错：ECONNREFUSED 127.0.0.1:8080

这是本章最值得记住的一节。

这个报错到底在说什么

翻译成人话：“我想连本机 8080 端口，但那个端口上没有任何程序在等着。”

注意：这不是 AI 坏了，也不是模型出问题了。它只说明一件事：两个程序没有连上。 模型甚至完全没参与这件事——消息还没走到它那儿。

我自己的日志里就有活生生的例子：机器人的定时问候全部失败，错误是”当前没有可用的 OneBot 连接”。原因不是问候逻辑写错了，而是 NapCat 那会儿没连上来。逻辑没问题，是连接断了。

排查顺序（照着走一遍就能定位）

Windows PowerShell：

  • 有输出且状态是 LISTENING → 框架起来了，问题在别处
  • 没有任何输出 → 框架根本没启动，去看框架的启动日志

去看机器人框架的日志，找 Bot ... connected 之类的字样。有就是连上了，没有就是没连上。

检查地址是否一致：NapCat 里填的反向 WS 地址，必须和框架实际监听的地址一模一样（端口、路径都要对）。差一个 /onebot/v11/ 都会失败。

其他常见错误

报错：[Errno 10048] ... 8080

意思是端口被占用——已经有一个程序占着 8080 了，你的框架起不来。

常见原因：上一次的进程没退干净。

Windows PowerShell：

现象：配置明明写了，程序却像没看见

这个坑值得单独说。我在配置文件 .env 里写了机器人的各种设置，结果跑起来全是默认值，改了半天没反应。

原因：我用的框架（NoneBot2）会读取 .env，但不会把它写进进程的环境变量；而我的代码是从环境变量读配置的。两边对不上，配置就静默失效了。

解决：在代码里显式加载一次 .env（Python 里就是 load_dotenv()）。

原理：这个坑的通用教训是——配置”改了没效果”时，先确认程序到底从哪里读配置。很多时候配置根本没进到程序里，而不是程序不认它。加一行打印把读到的值输出出来，比猜快得多。

七、总结

这一章我们做了一件关键的事：给大脑装上了耳朵和嘴。

回顾整条链路的三个角色，它们的分工值得再强调一次：

角色 本质 能不能换成别的
NapCat 登录 QQ 的”身体” 能（换任何支持 OneBot 的接入端）
OneBot 统一的”说话格式” 是标准，不用换
机器人框架 处理逻辑的”神经” 能（换别的框架）
Ollama + 模型 “大脑” 能（换别的模型）

四层之间全部通过标准地址/协议连接，任何一层都可以单独替换——这就是这套架构最漂亮的地方，也是它能被一个大学生一步步搭起来的原因：你不需要一次理解全部，只要保证每一层的接口对得上就行。

我这章最想留下的一个习惯

遇到报错时，先分清”是哪个程序之间的连接出了问题”，而不是一头扎进 AI 模型里找原因。

实际经验：我这章遇到的所有问题，没有一个是模型的问题，全是”两个程序没连上”或者”配置没读进去”。先确认连接，能省掉 80% 的无用排查。
