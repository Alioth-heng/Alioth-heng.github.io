第三章：让AI开口说话——本地TTS语音合成部署
Published in：2026-10-11 | category： 技术学习 AI 应用

前两章做完了，机器人能听、能想、能打字。但每次看它回一大段文字，总觉得少了点什么——它不会说话。
这一章给它装上嘴。

一、TTS 是什么：文字怎么变成声音

TTS = Text To Speech，文字转语音。听起来很魔法，但拆开看只有三步。

graph LR A["文字<br/>今天天气不错"] --> B["① 文本分析<br/>标出读音、停顿、语气"] B --> C["② 声学模型<br/>算出这段声音长什么样"] C --> D["③ 生成波形<br/>变成能播放的音频"] D --> E["音频文件<br/>.wav"]

第 ① 步：文本分析（把字变成”怎么读”）

计算机不认识汉字，它得先搞清楚这句话该怎么念。包括：

  • 每个字读什么音（多音字怎么办：”行”在”银行”和”行走”里不一样）
  • 在哪里停顿、哪里是问句要上扬
  • 数字、英文缩写怎么读（”2026” 是”二零二六”还是”两千零二十六”）

这一步的输出通常是音素（可以理解为”发音的最小单位”）或者拼音序列。

第 ② 步：声学模型（算出声音长什么样）

拿到读音序列后，模型要决定：这段声音的频率、时长、能量该怎么变化——也就是所谓的”声学特征”。

这一步决定了”听起来像谁在说话””是什么语气”。

第 ③ 步：生成波形（真正出声）

把上一步算出来的特征还原成人耳能听的音频波形，输出一个 .wav 文件。

原理：你会发现一个有意思的点——第 ① 步和语言有关，第 ②③ 步和音色有关。
所以”换个音色”换的其实是第 ②③ 步用的模型，而不是文字处理部分。后面讲音色选型时会用到这个结论。

二、为什么语音也要坚持本地

和第一章选本地大模型的理由一样，但到了语音这块，理由更硬：

  1. 隐私：要合成的可是聊天内容。既然前面已经费劲把模型搬到本地了，如果最后一步把内容发给云端语音服务，那整套隐私保护就白做了——最弱的一环决定整体的强度
  2. 延迟可控：云端 TTS 要走一次网络往返，还要排队；本地的延迟是固定的，可以自己优化
  3. 可控性：想缓存、想改采样率、想拼接、想换音色，全都在自己手里

代价是：要占用磁盘和算力。一个好点的语音模型动辄 1~3GB，而且合成时要吃显卡或 CPU。

三、我的音色选型之路（这一段最有参考价值）

这是我花时间最多的部分，也是我觉得最值得写下来的——因为它不是”照着教程做”，而是真实的取舍过程。

我先后试了四类方案，按我的体验排序：

方案 A：Piper（轻量，纯 CPU）

  • 优点：几十 MB，纯 CPU 就能跑，秒级出声，资源占用极小
  • 缺点：机械感明显，像导航语音
  • 我的评价：作为兜底很称职，但作为”阿晴的声音”不够

注意：Piper 的中文音色需要额外的拼音转换资源，它会在当前工作目录下找这个资源。我一开始目录套错了，报了个看不懂的错。教训是：这类工具报错时，先检查它的工作目录对不对，而不是怀疑模型坏了。

方案 B：Kokoro-82M（轻量，自然度更好）

  • 82M 参数，几百 MB，CPU/GPU 都能跑
  • 自然度明显好于 Piper
  • 我踩的坑：它的中文词表用的是国际音标（IPA），而很多示例代码走的是”注音”路径。表面上不报错，但生成的音频是残缺的——只有大约 8% 的音素被正确处理，出来的声音断断续续。这种”不报错但结果是错的”的坑，比直接报错难查十倍。

方案 C：GPT-SoVITS（声音克隆路线）

这是社区里最火的”用某人声音说话”的方案，理论上可以克隆任意音色。

我最终没有走这条路，原因值得单独说：

关于”角色音色”和”声音克隆”，必须讲清楚的一件事

很多人做 AI 机器人的初心是”让某个动漫角色陪我聊天”。这个想法很好理解，但到了音色这一步，有几件事必须分清：

普通音色调整 声音克隆
做法 换模型预置的音色、调语速音高、用自然语言描述语气 用真实人物的语音素材训练/微调出一个音色
需要素材 不需要 需要目标人物的录音素材
法律/授权 模型许可证允许即可 取决于素材来源
风险 低 高

关键的一点：如果目标是某个商业作品里的角色（比如某个游戏的角色），那么——

  • 这个角色的声音素材版权属于制作方，不是公开的免费资源
  • 就算你在网上找到了别人训练好的权重，那些权重往往也写着”禁止二次分发””禁止商用””数据版权归原作者”
  • 社区现成的权重库里，中文的角色音色往往根本没有（我去核实过，某个热门仓库里该作品只有英文和日文，中文目录是空的）

注意：我不会在文章里推荐任何未经授权的角色声音克隆方案，也不会提供获取渠道。这不是技术能力问题，是边界问题：个人自用不等于合法，而且这类模型一旦传出去，责任会跟着走。

我最后的选择：用官方开源、许可证明确（Apache-2.0）的通用音色模型，再配一句自然语言的”语气指令”来调情绪——比如”用明亮的年轻女声，语气清冷、略带傲娇地说”。

这样做的好处是：完全合规、随时可调、没有版权风险，而且调语气只要改一句话，不用重新训练任何东西。效果上确实不是”某个具体角色本人”，但它是我自己定义的那个角色，反而更贴合。

方案 D：Qwen3-TTS 0.6B（最终选择）

  • Apache-2.0 许可，2.38GB
  • 预置多种音色，支持自然语言指令控制语气（这就是我上面说的那句”清冷、略带傲娇”）
  • 我实测音色自然度和语气表现都明显好于前三个方案

最终架构是这样的——我把四个方案的优点组合了起来，做成一个三级降级链：

graph TD A["要合成的文字"] --> B{"主音色服务<br/>Qwen3-TTS（常驻）"} B -->|"成功"| E["输出音频"] B -->|"失败/服务没起"| C{"备用：克隆引擎<br/>GPT-SoVITS"} C -->|"成功"| E C -->|"失败/没权重"| D{"兜底：Piper<br/>纯 CPU，秒级"} D -->|"成功"| E D -->|"也失败"| F["不发语音，只发文字<br/>（机器人不会失声）"]

原理：为什么要搞这么复杂？因为语音是”锦上添花”的功能，绝不能因为它把主流程搞崩。
我在代码里定了一条硬规矩：语音链路的任何异常都必须被吞掉并降级，最坏情况只是”这条没有语音”，文字回复照常发出。做机器人是这样，做任何附加功能都该这样——附加功能永远不能拖垮主流程。

四、关键设计决策：把语音模型做成”常驻服务”

这是我这章做的最重要的一个工程决定，也是和前两章思路最大的不同。

问题：每句话都重新启动一次模型，行不行？

不行。我实测这个语音模型加载一次要 13~18 秒。如果沿用前面”每条消息启动一个进程”的做法，用户发一句”说”，要等将近 20 秒才听到第一帧声音——而且这 20 秒里大部分时间根本不是在合成，只是在加载。

解决：让它一直开着

我把它改造成了一个常驻的本地服务：

服务只监听 127.0.0.1:8765，不对外暴露，文本也绝不出本机。

原理：这个取舍的本质是——把”一次性的启动成本”摊到”多次使用”上。
只要你会反复用到一个很重的东西，就应该考虑让它常驻。这个思路不只适用于 TTS：模型服务、数据库、爬虫池子，都是同一类问题。
代价是它会一直占着资源（我这个约 2GB 显存），所以要想清楚”值不值”。对我这种机器人 7×24 在线的场景，显然值。

服务里还做了一个小优化：预热

服务启动后，我会先用两句短文本空跑一遍再正式对外提供服务。

为什么？因为第一次真正推理时，显卡要做一堆初始化（编译计算核、自动调优），这部分开销可能有好几秒。提前把它跑掉，用户第一次请求就不会撞上这个冷启动。

做了预热之后，服务对外可用的时间点会晚几秒，但用户感知到的第一次延迟明显下降——这个交换是划算的。

五、QQ 机器人里的完整调用流程

把语音接进机器人，链路是这样的：

graph LR A["AI 生成回复文字"] --> B["判断要不要发声<br/>（我设成带触发词才发）"] B --> C["文字先发出去<br/>（不让人干等）"] C --> D["清洗文本<br/>去掉表情、链接等"] D --> E{"缓存里有吗？"} E -->|"有"| I["直接用，0 秒"] E -->|"没有"| F["调常驻 TTS 服务"] F --> G["拿到 .wav 音频"] G --> H["作为语音消息发出"] H --> I

几个设计细节，都是踩过才想到的：

1. 文字先发，语音后到

代码里的顺序是：先把文字回复发出去，再去合成语音。这样用户马上就能看到回复，语音晚几秒到也无妨——体验上像是”对方又补发了一条语音”。

注意：这个顺序很重要。如果反过来（先合成再一起发），用户就要干等整个合成过程，体感差非常多。凡是”锦上添花”的东西，都要排在主体内容之后。

2. 缓存

合成很慢，但相同文本的结果是固定的。所以我把合成结果按”文本内容 + 音色 + 语气指令”做哈希缓存起来。同一句话第二次说，是 0 秒返回。

注意：缓存的 key 一定要把影响输出的所有因素都算进去。我一开始漏了语气指令，结果改了语气指令后仍命中旧音频，听起来”改了没生效”——和第二章那个”配置没读进去”是同一类错误。

3. 文本清洗

表情、链接、特殊符号要念出来会很怪，所以合成前会做清洗；如果清洗完没有任何可读内容（比如对方只发了一串符号），就直接跳过，不合成。

4. 触发方式

我做成了”带触发词才发语音”（比如发”说”或”语音”），而不是每条都发——语音会刷屏，而且每次都要等合成。功能设计上的克制，也是体验的一部分。

六、常见问题与排查

问题 1：声音延迟很高，怎么优化？

这是本地 TTS 最现实的问题。我实测的结果是：20 个字大约要 20 秒（RTF ≈ 4，意思是生成 1 秒音频需要 4 秒时间）。

先说结论：大部分你以为有用的优化手段，实测都没用。 我把排查过程写下来，比直接给结论更有价值。

第一步：先判断瓶颈在哪（这一步不能跳）

Windows PowerShell（在合成过程中采样）：

我看到的結果是：

GPU 利用率只有 35~40% ——这说明显卡大部分时间在空转等 CPU。也就是说瓶颈在 CPU 侧的 Python 代码循环，不在显卡算力。

这个判断直接决定了后面该试什么：

优化手段 我的实测结论 为什么
关掉随机采样（贪婪解码） 无效，反而略慢 瓶颈不在采样这一步
装 flash-attn 加速注意力 基本无效 它加速的是 GPU 侧，而 GPU 本来就在闲着
模型量化（8bit / fp16） 无效 显存带宽不是瓶颈
多进程并行 不改善延迟 只提升吞吐，单条请求还是那么久
限制合成字数 有效 延迟和字数近似成正比，最直接的杠杆
启用缓存 有效（重复句 0 秒） 绕过计算本身

原理：先测量再优化。如果我不看 GPU 利用率就跑去装 flash-attn，可能折腾半天什么都没改变。
判断”是算力不够还是有人在等”，只需要看一眼利用率：接近 100% 说明算力吃满（加硬件/降模型），只有 30% 说明有东西在空转（查调度和代码路径）。这一个动作能省掉你 80% 的无效尝试。

最后怎么解决的：接受这个延迟，但把合成字数上限调小，并充分利用缓存。再加上前面说的”文字先发”，实际体验完全可以接受。

问题 2：模型太大，磁盘/显存吃不消

  • 磁盘：所有模型、缓存、临时音频都放到非系统盘（我的都在 D:\AI_Models\...）。很多工具默认会把缓存写进用户目录（C 盘），需要显式改环境变量把它们指走
  • 显存：常驻服务会一直占着显存。我这个约 2GB，和本地大模型并存没问题（合计约 6GB / 8GB），但如果你显存更小，可以考虑用纯 CPU 的轻量方案（如方案 A/B）

注意：改缓存位置这件事要在下载第一个模型之前做。事后搬家很麻烦，而且容易漏掉某个工具的缓存目录。具体做法和第一章 5.2 节设置环境变量是一样的思路——凡是”下载/缓存”，先问一句”它会写到哪去”。

问题 3：CPU 占用高 / 电脑变卡

语音合成是重计算任务，合成时 CPU 或 GPU 会有一阵子满载，这是正常的。

如果影响使用：

  • 限制并发（我用一个锁保证同一时刻只有一个合成任务在跑）
  • 限制合成字数
  • 把触发方式设成”手动触发”而不是”每条都发”

七、总结与未来扩展

到这里，这个机器人就完整了：

能力 由什么提供
听（收消息） NapCat + OneBot
想（生成回复） Ollama + Qwen3.5-4B
说（语音） 本地 TTS 常驻服务

全部跑在本机，不依赖任何在线服务，聊天内容一步都没有离开过这台电脑。

回看这三章，我真正学到的东西

技术细节会忘，但有几个判断习惯我觉得比命令更值钱：

  1. 先分清”是哪两个东西之间的连接出了问题”——我这章遇到的报错，几乎全是连接问题，不是 AI 的问题
  2. 先测量再优化——一句 nvidia-smi 就能避免半天无用功；不知道瓶颈在哪的优化都是猜
  3. 附加功能不能拖垮主流程——语音挂了就只发文字，这条规矩让整个系统稳定了很多
  4. 重复用到重东西时，考虑让它常驻——把启动成本摊薄
  5. 合规边界要自己守住——能用合规方案达到 80 分，就别为了 90 分去踩线

还能往哪扩展

  • 记忆系统：现在对话历史有窗口限制，可以把重要信息存进数据库，让机器人记住你很久以前说过的话
  • 主动行为：我给机器人加了定时问候（早安/午饭/晚饭/晚安），用任务调度 + 数据库去重保证不会重复发
  • 图片能力：本地模型支持视觉输入的话，可以让它看图说话
  • 换个更强的模型：显存更大可以考虑 7B/8B，对话质量会再上一个台阶
  • 多端接入：因为中间用的是标准协议，把 QQ 换成其他平台，机器人逻辑基本不用改

系列总结

《从0搭建属于自己的AI QQ机器人》三章到这里结束：

  • 第一章：让电脑跑起本地大模型（Ollama）
  • 第二章：把它接进 QQ（NapCat + OneBot + 机器人框架）
  • 第三章：让它开口说话（本地 TTS）

我最初只是想搞清楚”这些 AI 到底是怎么跑起来的”。做完之后最大的感受是：

这些看起来很唬人的东西，拆开之后每一步都是普通人能理解的。 难的从来不是某个具体命令，而是你不知道”这一步为什么要做”。所以这个系列的每一节我都尽量先说清楚”为什么”，再说”怎么做”。

如果你跟着做下来了，那么恭喜——你现在有了一个完全属于自己的 AI 机器人，而且你知道它的每一个零件是怎么工作的。这比直接用现成服务，要有意思得多。
