从记事本开始理解桌面 Agent：Python、UI Automation 与 Harness 入门
Published in：2026-10-25 | category： 技术学习 Agent 入门

刚开始学习 Agent，很容易被一串名词绕晕。先把目标缩小：让电脑打开记事本，输入学习笔记，再保存到指定文件夹。

你手动做这件事只需要几十秒，但程序怎么知道哪个是记事本？编辑区为什么叫 Document？点了保存就算成功吗？这样的程序已经是 Agent 了吗？

这篇文章沿着本次学习路线，把这些问题串起来。你只需要知道 Python 的变量、函数和循环。递归也不用怕，我们会用图理解。

本文控件属性来自本次实际观察，不是所有 Windows 版本的固定答案。自动化脚本已编写并做过语法检查，不将其描述为已在所有版本实测通过的方案。教学配图不代表实际执行截图。

一、UIA：给软件界面提供可查询的结构

人能看懂屏幕上的按钮，程序则需要一种访问方式。除了识别截图，还可以读取应用暴露的控件信息。Windows UI Automation，简称 UIA，就是访问界面元素及其操作能力的一套接口。

把它想成图书馆目录：不用猜每本书的位置，可以先查询它叫什么、属于哪里。比喻只是帮助理解，UIA 本身不是文件目录。

  • Client：访问界面的客户端，这里是 Python 自动化程序。
  • Provider：应用或框架用来暴露控件信息的实现。
  • Element：控件树上的一个元素，例如窗口、按钮。
  • Pattern：元素支持的能力，例如调用动作、访问文本。

不是所有界面都提供完整信息。自绘区域、某些框架或权限差异，都可能让控件无法读取。统一接口不能理解成所有软件一定兼容。技术背景见 微软 UIA 概览。

1. 列窗口，不等于列所有运行进程

Desktop 是访问桌面的入口，uia 指定后端，windows() 查询顶层窗口，visible_only=True 限定可见窗口。

本次结果中除了记事本，还有任务栏、通知和 Program Manager。所以它不是进程清单，也不是任务栏按钮清单。Program Manager 通常是 Explorer 管理的桌面外壳窗口，不是“任务管理器”；本机归属可按 PID 到任务管理器核对。

某个软件运行却没出现，可能是藏在托盘、没有主窗口，或标题根本不是软件名。先展开界面、按 PID 查找，再考虑用 visible_only=False 看隐藏窗口。被别的窗口挡住通常不等于不可见。

2. 控件树属于记事本，TXT 本身没有关闭按钮

TXT 存放文本；记事本提供编辑区、菜单、标签页和按钮。Name='文本编辑器' 是控件名称，不是正文。

属性 回答的问题 注意事项
Name 它叫什么？ 可能为空、可能随标题变化
ControlType 属于什么控件类型？ 本机编辑区为 Document，而非 Edit
AutomationId 应用提供了什么标识？ 可能为空，不保证全桌面唯一
ClassName 控件由什么类实现？ 可能随框架版本变化
Handle 当前是哪一个窗口？ 重开后可能变化，并非所有元素都有原生句柄
PID 属于哪个进程？ 一个软件可能涉及多个进程

属性用于定位，树表示层级，Pattern 表示能力。 Invoke 表示调用动作，Text 用于文本访问，Value 用于控件值访问。不能只凭类型就假定所有模式都支持。见 微软控件模式说明。

3. 递归到底是什么？

递归就是函数调用自己。在树上，它相当于：先打印当前节点，再对每个子节点重复这个动作。

这是省略异常处理和节点上限的讲解片段。窗口为第 0 层，进入子节点就加 1；一个分支看完，再看下一个。max_depth=3 只到第 3 层，不能说是“全部控件”。菜单展开、标签切换后，树还可能变化。微软控件树文档说明了它的动态性质。

三、从启动到保存：动作之外，还要检查结果

1. 发出启动命令，不代表窗口已就绪

这只发出启动请求。新记事本可能复用旧窗口、创建标签页或恢复旧内容。练习脚本先记录已有句柄，再等待唯一新窗口；不能确认目标就停止。

这是保守策略：复用旧窗口时可能超时。应自行保存旧工作、关闭窗口后重试，或进一步实现可靠的标签页定位，而不是随机接管旧窗口。

2. 先确认编辑区，再输入

完整脚本优先找 Document，再兼容 Edit，检查可见、可用和唯一性，读取已有正文，非空则停止。旧控件是否支持相同文本读取接口仍需检查；兼容类型不等于兼容所有版本行为。

这里的关键是：UIA 定位对象，键盘输入依赖焦点。 运行时保持屏幕解锁，不切换窗口。type_keys 中 ^、+、% 等代表快捷键语法，任意文本要先正确转义。

3. 保存需要明确路径和正确对话框

随后检查对话框归属，定位文件名框，输入完整路径，核对输入值，调用保存按钮。标准对话框里常见 AutomationId=1001 的文件名框和 AutomationId=1 的保存按钮，但必须观察本机结构，不能假设所有应用相同。

脚本输出到学习子文件夹上一级的 output，文件名带时间戳，避免重复练习覆盖以前的成果。生产工具还要处理并发冲突、覆盖确认和路径边界。

4. 文件存在，还不算完成

完整练习也尝试常见其他编码。比较时统一 CRLF 和 LF 换行，但不随意删空格或段落。验收证据应是正确路径出现文件，并且磁盘正文正确，不是“按钮点过了”。

四、增加错误检测：让失败有清楚的出口

这张图是检查设计，不意味着现有脚本已覆盖所有分支。例如输入后的即时正文核对，还可以继续增强；目前主要依靠最终磁盘验收。

固定 sleep(5) 是“无论如何等五秒”；条件等待是“最多等十五秒，满足条件就继续”。

probe 是检查函数：暂未就绪返回 None，成功返回对象。不要吞掉所有异常，把代码写错也当成“还没等到”。轮询超时不能强行中断卡住的单次底层调用；严格总时限还需额外运行隔离。

安全停止是不再向不确定目标输入、不继续保存，保留现场并说明原因；它不等于自动撤销已完成动作。脚本失败时输出原因、返回非零退出码。

五、深入理解 Agent 和 Harness：一个会做判断的同学，为什么还需要实验室？

我们已经能让 Python 操作记事本。现在把问题往前推一步：用户只说“把今天的学习笔记保存好”，谁把目标拆成行动？遇到弹窗谁来判断？谁真的按下保存，又是谁确认没有保存错？

先约定用词：本文讨论的是以语言模型参与决策的 Agent。 更广泛的计算机科学中，Agent 不一定依赖大模型。不同产品也会把“Agent”用于整个系统，而不只是决策部分。

1. 先去一次大学实验室：理解四个角色

老师布置实验：“测出这根金属丝的电阻，并提交可信的实验记录。”老师给的是目标，没有告诉你每次该转哪个旋钮。

Agent 像做实验的同学。 他读任务、看仪器读数，判断该换量程、重新测量，还是整理结果。关键不是“会说实验怎么做”，而是能根据反馈继续选择行动。

Harness 像实验室围绕这位同学提供的一整套运行安排。 它不只是一张桌子：还有仪器使用接口、实验记录、可用设备清单、操作限制、超时规则，以及把新读数交回来的机制。它让判断能持续接上实际行动。

工具像具体仪器。 万用表负责测量，电源负责供电；对应我们的 list_windows()、inspect_controls()、save_as()。工具执行明确动作，不需要承担整个任务规划。

环境像被测电路。 它是会被操作、会发生变化的外部对象。在本项目中，就是 Windows、记事本和磁盘文件。

实验室比喻 本项目对应 主要回答
老师的实验要求 用户目标与验收标准 最后要得到什么？
做实验的同学 Agent 的决策部分 根据目前情况，下一步做什么？
实验室运行安排 Harness 怎样把决定执行、记录并接回结果？
万用表等仪器 Python/UIA 工具 这一个具体操作怎样完成？
被测电路 Windows 和记事本 外部实际发生了什么？

这个比喻有边界：Harness 不是另一个“无所不知的老师”，也不必是第二个模型。它主要是软件机制；是否提供强制限制，取决于实际实现，不能因为叫 Harness 就假定已经安全可靠。

2. 为什么“有个聪明模型”还不够？再想想司机和汽车

让一个很懂交通规则的人坐在空地上，说“开到图书馆”，他也到不了。会判断路线，不等于拥有发动机、方向盘和路面反馈。

在这个比喻里：模型提供判断能力，工具接口像方向盘和踏板，外部环境是道路，Harness 则像把驾驶输入、传感信息、仪表记录和执行机制接起来的软件控制系统。用户给出目的地，Agent 的决策部分持续选择路线和行动。

同样，模型输出“我已经点击保存”只是文字。必须有运行程序识别操作请求、调用工具、拿到真实结果，再交回模型。否则它只是在描述开车，没有车真的移动。

也别把两者想成互相独立的两个机器人：实际系统中，决策循环往往正是由 Harness 驱动的。一次模型调用给出下一步；Harness 让下一次观察和调用继续发生。

3. 澄清一个容易混淆的边界：Agent 不是只有模型，Harness 也不等于电脑

“Agent 负责判断、Harness 负责运行”是职责划分，不是说每个系统一定有两个同名文件夹。常见语境里，Agent 指模型、指令、工具与循环共同构成的系统；我们为了讲清分工，才把里面的决策部分单独拿出来。

4. 跟着一次保存失败，看清谁在做什么

下面是用于教学的假设过程，不是已经接入模型运行的日志。用户目标是“保存今天的学习笔记”，而第一次保存后文件没有出现。

轮次 Agent 的选择 Harness 与工具实际做的事 返回的证据
1 先看看有哪些窗口 调用窗口查询工具 找到一个明确的记事本窗口
2 查看它的编辑区 查询目标控件树并返回属性 发现可用的 Document，正文为空
3 输入笔记，然后读取确认 工具设置焦点、输入、读取正文 编辑区正文与预期一致
4 请求另存为到目标路径 检查路径与窗口归属，执行保存 保存动作已提交，文件尚未出现
5 不急着宣布完成，先检查弹窗 再查询目标窗口及其对话框 发现路径不存在的提示
6 在允许目录内创建所需子目录后重试 若工具权限允许则执行，并限制次数 文件生成，读取后正文一致
7 根据证据报告完成 记录最终状态、路径与验收结果 完成记录可追溯

第 6 步不是“模型想做什么都能做”：没有授权的目录创建工具，就应该停止并说明缺少的能力。遇到陌生弹窗也不是一律点确定，而是先观察、确认含义和允许范围。

还要注意：Agent 决定重试，不代表 Harness 必须放行。如果已经超过最多重试次数，Harness 应返回限制错误，避免一直绕圈。

5. Harness 具体忙些什么？把它当成实验室的六本台账

第一本：任务本——目标和上下文。 把用户要求、已观察到的状态、工具说明组织成模型能读取的输入。就像实验前知道“测电阻”，而不是只拿到一句“继续”。上下文不是把所有日志无限堆进去，而是保留当前决策需要的信息。

第二本：工具借用登记——工具协议与调度。 列清工具名称、参数、返回值，检查模型给出的参数，再调用真实函数。模型提出 save_as(path=...)，不等于操作系统已经执行了保存。

第三本：实验记录——状态与历史。 保存已选择的窗口、目标路径、输入结果和错误。状态不是永久正确的：上次窗口句柄有效，不代表这次还有效；恢复任务后要重新观察。

第四本：操作规程——运行边界。 例如只允许写入学习目录、已有正文时拒绝替换、文件存在时拒绝覆盖。实际检查应在可信工具或运行层落实。提示词像“请遵守实验室规则”的告示，路径校验才像门禁；告示不能代替门禁。

第五本：计时和故障登记——预算、超时与恢复。 限制工具等待、循环步数和重试次数，区分可重试错误与需要停止的错误。模型请求“再试一次”时，预算仍然有效。重复输入文字可能把正文写两遍，所以重试前应检查已有状态，不能盲目重放所有动作。

第六本：验收单——验证与完成条件。 让确定性代码检查文件路径和正文，把证据返回决策部分。Agent 可以提出“完成”，但系统可以要求先通过验证器，再接受完成状态。模型说得自信不是验收证据。

这些职责可以拆成多个模块，不一定全写在一个类中。有些简单项目只实现其中几项，因此我们应该问“它具体管理了什么”，而不只问“它有没有 Harness”。

7. 长任务为什么更需要 Harness？想想小组作业交班

两分钟完成的记事本任务，你还记得刚做了什么；持续几小时的项目，则像小组成员轮班写课程设计。新同学接班时，如果只听到“前面做了一些，你继续”，很容易重复劳动或误把半成品当完成品。

所以要留交班单：目标是什么、完成到哪里、哪些检查通过、哪里失败、下一步建议做什么。Harness 可以保存这些记录，并在恢复时重新提供必要上下文。记录能帮助继续工作，但不能保证摘要没有遗漏，也不能代替重新核实环境。

Anthropic 的长任务 Harness 文章讨论了跨会话进度衔接与过早宣布完成的问题。对应到我们的练习，哪怕记录写着“已经保存”，恢复后也应检查文件，而不是直接相信一句历史结论。

8. 脚本、工作流、Agent 怎么选？像菜谱和厨师

照着确定的菜谱做同一道菜，固定脚本通常很合适。菜谱允许根据温度和时间走不同分支，也仍然可以是脚本，不需要因为有 if 就叫 Agent。

如果厨房用预先定义的流程安排多个模型步骤，例如“模型生成笔记 → 固定脚本保存 → 固定代码验收”，这是带模型的工作流。用了模型，也不一定由模型决定流程。

如果食材和现场情况不断变化，需要“厨师”观察后选择做法，就更接近本文的模型 Agent：它在允许范围内决定调用哪个工具、补查什么信息、何时停止。厨师仍然要遵守厨房设备与操作边界。

方案 谁主要决定执行路线？ 适合什么情况？
固定脚本 预先写好的代码 记事本结构稳定、重复保存同类内容
带模型的工作流 代码组织步骤，模型完成局部任务 内容生成灵活，保存和验收步骤确定
模型 Agent 模型根据观察动态选择，Harness 管理执行 路径不固定，需要多轮调查与判断

这与 Building effective agents 对预定义工作流和模型动态控制流程的区分一致。选择 Agent 会增加成本、延迟和调试难度；应从任务需求出发，不是越自主越高级。

终端错误与诊断文件 日志和故障线索 结构化状态与恢复机制
main() 的固定步骤 当前脚本的流程控制 尚未加入模型选择下一步的循环

因此，我们已经造出了部分工具和运行积木，还没有因此完成一个模型 Agent。下一次实验可以先把“观察”“输入”“保存”“验证”拆成清晰接口，再考虑接入模型，不必推倒已有代码。

10. 用三个场景检验自己是否理解

窗口没出现，谁决定换一种查询方式？ 决策部分可以根据错误选择新策略；Harness 返回查询结果并限制总尝试次数。如果恢复策略事先写死在代码里，也可以由运行层直接完成，并非每次重试都必须经过模型。

Agent 请求保存到不允许的目录，谁阻止？ 可信运行层或工具实现拒绝请求。就像实验室门禁不因为同学说“我觉得可以”就放行。

Agent 说完成了，但磁盘正文不一致，信谁？ 信验证证据，保留“未完成”状态。像交实验报告，不能用“我感觉测好了”代替测量数据。

读完之后，希望你能把这段话讲给室友：Agent 的决策部分像做实验的人；Harness 负责把观察、工具、记录、边界和循环接起来；工具是真正执行具体操作的仪器；是否完成，要看外部结果和验收。 这几个角色协作，才让“会回答”走向“能持续做事”。
