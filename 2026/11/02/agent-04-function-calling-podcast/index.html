Agent 第四课｜用一集播客讲懂 Function Calling：模型怎样选工具、填参数，再真正完成任务
Published in：2026-11-02 | category： 技术学习 Agent 入门

本期形式：单人口播讲稿，附可对照操作的实验代码。正文适合连续阅读或朗读；代码作为节目笔记查看。本篇交付的是文字讲稿，不包含音频文件。

这是总学习进度中的第四课，也是本周工具调用主题的第一讲。本期重点是 Function Calling，并沿着它看清最小 Agent 的全流程。本周暂不引入 MCP。

大家好，欢迎回到我们的 Agent 学习笔记。

前面几节课，我们已经让 Python 和记事本打过交道：找到窗口，找到编辑区域，输入文字，再把它保存下来。今天，我们要让这套流程多一个决策者——大语言模型。

想象你对电脑说：“创建一份学习笔记，写上今天学习 Function Calling，再用记事本打开，让我检查。”

如果只是普通聊天，模型可以回答“好的”。但你会发现，屏幕没变化，文件夹里也没有新文件。这就是今天要跨过的那道门：一句自然语言，怎样变成一次真实的操作？

先把本期最重要的一句话记下来：模型生成工具调用请求，程序负责检查和执行，工具结果再回到模型。

开场：先把四个角色分清楚

我们先不急着运行代码。你可以把这个小系统想成一个工作小组。

用户负责提出目标：“帮我创建学习笔记。”

模型负责理解任务，决定接下来请求哪个工具，以及给它什么参数。

Harness 是你编写的外围程序。它接收模型请求，检查工具名称、参数和权限，调用真正的函数，并整理执行结果。

工具是做具体事情的函数。例如写文件、读文件、启动记事本。

把这个分工放进我们的例子里，就是：你提出目标，模型申请写文件，Harness 检查路径并执行写入，再把成功或失败告诉模型。

这里先停一下。“模型说自己做了”和“程序验证它做成了”，是两件事。 后面每个步骤都围绕这个区别展开。

第一步：先给工具起名字，并说明它能干什么

主持人：假如我给你一把从没见过的工具，既没有名字，也没有说明，你能准确使用吗？模型也需要接口说明。

我们先设计三个工具：

工具名称 负责的事情 主要参数
write_file 在学习目录内创建文本文件 path、content
read_file 读取学习目录内的文本文件 path
open_notepad 用记事本打开已存在的文本文件 path

注意，这里我们设计的是“直接写文件，再用记事本打开”。前几课采用的是“通过界面输入并另存为”。两种做法可以满足不同练习目标。本课选择直接写文件，是为了把注意力集中到模型如何提出工具请求。

下面是 write_file 的声明。先看名字和中文描述，再看参数，不需要一下子背下来。

口播时，我们可以这样解释这段结构：最外层说，这是一项函数工具。里面的 name 是程序匹配工具的标识，description 说明使用场景。parameters 则是一张表格，规定需要填写什么信息。

type: object 表示参数整体是一个对象。两个 string 表示路径和正文都应该是字符串。required 表示不能漏项。additionalProperties: false 表达“不接收额外字段”的约束。

这类参数描述采用 JSON Schema。请留意：描述中的权限要求，以及 Schema 中写下的规则，都需要 Harness 在执行前落实检查。 不能因为写了一句“只能访问学习目录”，就认为模型或操作系统会自动替我们限制访问。

还有一个容易混淆的地方：工具声明里没有真正的文件写入代码。它是接口手册。真正执行的 Python 函数，是另一个部分。

第二步：把用户请求和工具说明一起交给模型

现在我们有了工具手册。接下来，程序调用模型接口时，要把对话消息和工具声明一并发送。

你可以把请求分成三部分理解：

用户消息可以是：

请创建“学习笔记.txt”，正文为“今天学习 Function Calling”。随后用记事本打开这个文件。

这里还有一个前提：运行的模型和服务需要支持工具调用。能普通聊天，并不能直接证明它能返回工具调用结构。我们后面的阶段一，就是专门验证这件事。

对 Ollama 来说，本课使用 /api/chat 接口的 tools 字段，并关闭流式输出，方便初学者先观察完整返回。接口字段和工具消息用法可对照 Ollama 官方工具调用文档。

第三步：模型怎样选择工具？

主持人：模型看到“创建文件”，是像我们写的 if 语句一样，遇到某个关键词就固定选择工具吗？

通常不是。模型根据用户请求、上下文以及工具说明，生成下一段输出。输出既可能是给用户的文字，也可能包含工具调用。

“创建并写入”通常对应 write_file；“看看文件内容”通常对应 read_file；“让我在记事本里看一下”通常对应 open_notepad。

这里的“通常”很关键。模型可能选错，也可能选择先提问。例如用户只说“帮我整理一下那个文件”，却没有说明文件名，模型没有足够信息时就应该询问，而不是随便编一个路径。

工具描述也会影响选择。如果三个工具都写成“处理文件”，它们之间的边界就很模糊。把“何时使用、需要什么输入、有哪些限制”写清楚，比给工具起一个很酷的名字有用。

至于底层机制，模型仍然在预测和生成 token。所谓 Function Calling，是让输出遵循工具调用协议，并由运行时解析成可供程序处理的结构。能够输出符合格式的请求，不代表请求内容必然正确。

第四步：把自然语言转换成具体参数

模型选择 write_file 以后，还要填写参数。

用户说“创建学习笔记.txt”，模型据此生成 path。用户说“正文为今天学习 Function Calling”，模型据此生成 content。

下面是一条用于讲解的简化调用请求；实际接口响应外层还会包含其他字段：

请在脑海里按一下暂停键。

到这里，磁盘上还没有因为这条消息就自动出现文件。模型输出的是“我要调用这个工具，请使用这些参数”。它像填好了一张申请单，而执行这张申请单的程序还没开始工作。

同时，模型返回一段包含 JSON 的普通文字，也不能直接当成接口级工具调用成功。实验时，我们需要检查返回消息中的 tool_calls 字段，而不是看到正文里出现了大括号就宣布通过。

第五步：Harness 接过申请单，先检查，再执行

接下来终于轮到你写的程序出场。

Harness 首先检查名称。write_file 在允许的工具表里吗？如果模型编出 delete_everything，程序应该拒绝这个未知工具。

然后检查参数。它是对象吗？path 和 content 都在吗？类型是字符串吗？有没有意外的额外字段？

再检查权限。路径是不是相对路径？解析后的真实目标还在指定学习目录里吗？后缀是不是允许的 .txt？文件已经存在时，是否应该拒绝覆盖？

最后，满足条件才执行。

为什么要“解析路径”？因为 ../其他目录/文件.txt 看起来是相对路径，却可能走出允许范围。简单检查字符串是否以某个目录名开头，也不足以证明路径安全。后续实现时，要检查解析后的路径与允许根目录的关系，并考虑符号链接或 Windows junction 等情况。

同样重要的是工具分发：我们会使用显式映射表，让固定名称对应固定函数。不要把模型生成的文字交给 eval 或 exec；启动记事本也无需让模型拼接任意命令行。

这些限制最终还受进程本身的操作系统权限影响。教学用 Harness 的目录检查，是一层明确边界，不等于完整的系统隔离沙箱。

失败不是没有价值的结果。它告诉模型：刚才那个计划没有完成，下一步需要调整。

不过也不要把每个错误都无限重试。路径越界属于权限拒绝，不能靠换写法绕过去。参数缺失可以补齐后重试；文件已存在时，可以读取现有内容，或者在用户目标允许时选择一个新文件名。

第七步：把模型自己的请求和工具结果一起放回对话

工具执行完以后，程序必须维护对话历史。

先保留模型刚才发出的 assistant 消息，其中包括工具调用。再追加 role 为 tool 的结果消息。对于本课使用的 Ollama 接口，结果消息可以通过 tool_name 指明工具，content 放序列化后的结果。

这里的 response、result 来自前面的模型响应和真实执行结果，这个片段用于解释消息组织，并非独立脚本。

为什么要保留模型自己的请求？因为下一轮模型需要知道：我申请过什么操作，程序对哪次操作给出了什么结果。如果只塞进一条“成功了”，缺少上下文，模型就容易把结果归到错误的事情上。

不同厂商的协议可能要求通过调用 ID 来关联结果。学习时先认准当前接口，不要把不同协议的字段混在一起。本期 Ollama 消息组织方式以 官方示例 为准。

第八步：再调用一次模型，让它依据结果决定下一步

现在模型看到了“文件创建成功”。用户的目标完成了吗？

还没有，因为用户还说了“用记事本打开”。于是模型下一轮可以申请：

这次 Harness 依旧检查路径、文件存在性和工具权限，再启动记事本。

这里又有一处值得暂停：启动命令已提交，不等于界面已经打开正确文件。 如果工具只拿到一个进程编号，返回值就应该说明“已请求启动”。要声称“记事本已显示目标文件”，还需要窗口或界面层面的证据。前几课学的 UIA，恰好可以在这个地方帮助我们验收。

同样，文件存在也不等于正文正确。需要时，可以先通过 read_file 读取文件，比较实际内容，再让模型总结结果。

每一次工具执行都会改变模型可利用的信息，所以程序需要多次调用模型。我们把“调用模型、执行工具、追加结果、再次调用”这个循环叫作 Agent Loop。

工程上还要给它设置停止条件：最大模型轮数、最大工具调用数，以及超时或其他预算。模型没有继续提出工具调用时，可以结束循环，但这只能证明它停止了请求，任务是否真的完成，还要看事先定义的验收标准。

操作四：看结果时，区分四种情况

观察结果 能说明什么 下一步检查
有正确 tool_calls，名称和参数符合要求 本次结构化调用实验通过 进入 Harness 实现
只有“好的，已创建”的文字 没有拿到结构化工具请求 检查模型能力、tools 字段与提示词
有工具调用，参数缺失或不一致 协议有输出，但任务参数没有通过验收 查看实际参数，调整描述并复测
HTTP 错误、连接失败或超时 服务或请求没有完成 查看服务、模型名、端口和错误正文

验证“选工具”时，再提供三个工具声明，并分别输入“创建笔记”“读取笔记”“打开笔记”。记录它选了谁。最后加入“解释一下 Function Calling”这类不需要操作文件的问题，看看模型是否会不必要地调用工具。工具选择和参数生成，应该分开观察。

接下来的三阶段，分别验收什么？

主持人：第一阶段拿到了“申请单”，后面三阶段才逐步把行动能力接起来。我们保持原定安排，不把所有功能一次塞进第一讲。

阶段 建议时间 实际产出 通过标准
1．验证 Ollama 工具调用 45 分钟 工具声明、原始消息、参数检查 返回真实 tool_calls，工具名和参数满足要求
2．编写最小 Harness 60 分钟 写文件、读文件、打开记事本三个受限工具 合法请求能执行，越界和错误参数能拒绝
3．实现 Agent Loop 60–90 分钟 对话历史、结果回传、循环与调用预算 模型能依据成功或失败结果调整下一步
4．测试与故障注入 45–60 分钟 故障用例、日志和任务验收记录 错误有反馈，权限不被绕过，完成情况有证据

阶段二先脱离模型，手动调用工具函数。这样一旦出错，你能判断是函数实现问题，还是模型生成请求的问题。

阶段三再接入模型，打印每轮的工具名、参数、执行状态和耗时。你应该能读懂整个过程，而不只是看到一句“任务完成”。

阶段四故意制造错误：漏掉正文、传入数字路径、请求目录外文件、重复创建同名文件、读取不存在的文件，以及让模型反复调用工具。分别验证参数拒绝、权限拒绝、正常错误回传和预算停止。

记事本验证也要包含一种情况：进程启动了，但没有证据证明目标文件已正确显示。工具必须如实描述验证层级。

收尾：用三个问题检查自己是否理解

最后，我们回到开头那个小任务。

第一问：模型返回 write_file 和两个参数，文件就一定存在了吗？

答案是没有。还需要 Harness 执行，并核对工具结果。

第二问：在工具描述里写“禁止访问学习目录之外”，就能保证权限吗？

答案是不能。程序必须做路径与权限检查，并结合实际运行环境的权限边界。

第三问：为什么写完文件，还要再调用一次模型？

因为工具结果提供了新的事实。模型需要依据这个事实，判断继续读取、打开、处理错误，还是向用户报告完成。对于这个教学任务，读取核验和打开通常还会带来更多轮调用。

今天你已经看到了最小 Agent 的骨架：用户给目标，模型提出操作，Harness 把关执行，结果进入下一轮决策。

接下来我们先完成阶段一，亲眼看看本地模型返回的那张“工具申请单”。等这一步稳定了，再接上真正的文件操作。
